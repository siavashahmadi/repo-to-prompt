repo-to-prompt
How It Works

A TypeScript CLI tool that recursively walks a codebase, filters files, estimates sizes, and formats everything into a single structured output. Built for developers who want to share full project context efficiently.

TypeScript Node.js CLI Tool File Systems Algorithms

What It Does Overview

repo-to-prompt is a command-line tool that takes a directory as input and produces a single text file containing every relevant source file, concatenated with clear separators and a metadata header. Think of it as a "snapshot" of a codebase.

High-Level Behavior

  1. You run it on a project folder
  2. It walks every file recursively, skipping ignored paths (node_modules, .git, etc.)
  3. It reads each file and detects if it's binary
  4. It estimates the total size in tokens (characters ÷ 4)
  5. If a size budget is set, it trims the largest files first
  6. It formats everything with headers and file delimiters
  7. It writes to stdout, a file, or the clipboard

Example Usage

# Pack current directory to stdout
node dist/index.js .

# Save to a file, markdown format, with a directory tree
node dist/index.js ./my-project --output context.md --format markdown --tree

# Only TypeScript files, cap at 80,000 tokens
node dist/index.js . --include "**/*.ts" --max-tokens 80000

# Only files changed since last commit
node dist/index.js . --diff HEAD~1 --copy

Execution Pipeline Architecture

Every time the CLI runs, it executes the same 8-stage linear pipeline. Each stage has a single responsibility and passes its output to the next. This is a classic pipeline pattern — easy to reason about, test, and extend.

1
config.ts

Load Config

Reads .repo2prompt.json from the target directory if it exists. Returns an empty object on missing file. CLI flags override everything from this file.

2
filter.ts

Build Ignore Filter

Stacks three layers of ignore rules: built-in defaults (node_modules, .git, dist…) → .gitignore content → user-supplied --exclude patterns. Uses the ignore package for gitignore-compatible matching.

3
walker.ts

Discover Files

Recursively walks the directory tree (DFS), applying the ignore filter at each node to prune entire subtrees early. Returns a flat list of { absolutePath, relativePath } entries.

4
summarizer.ts

Read File Contents

Reads each file in batches of 50 concurrent reads (capped to avoid file descriptor exhaustion). Detects binary files by extension and by scanning the first 512 bytes for null bytes. Truncates files exceeding --max-file-lines.

5
tokenEstimator.ts

Estimate Total Size

Concatenates all non-binary file contents and applies the heuristic: tokens ≈ characters ÷ 4. Produces a single integer representing the estimated total output size.

6
index.ts

Apply Token Budget

If --max-tokens is set and the total exceeds it, a greedy algorithm drops or partially truncates files — largest first — until the budget is satisfied. Mutates the in-memory FileBlock array.

7
formatter.ts + tree.ts

Format Output

Assembles the final string: metadata header → optional ASCII directory tree → one formatted block per file. Plain format wraps files with === path ===. Markdown format uses ## heading + fenced code blocks with language identifiers.

8
index.ts

Write Output

Writes to a file (--output), copies to the clipboard (--copy), or streams to stdout. Always prints a summary line to stderr regardless of output destination.

Module Breakdown Architecture

The project has 7 source modules, each with a single clearly-defined responsibility. This is the Single Responsibility Principle in practice.

🚀

index.ts

CLI entry point. Orchestrates all other modules. Owns the token budget loop. Handles output routing (file / stdout / clipboard). 225 lines.

⚙️

config.ts

Loads .repo2prompt.json. Returns empty config on missing or invalid file. Defines the Config interface used across the app.

🚫

filter.ts

Builds the stacked ignore filter. Exports DEFAULT_IGNORES. Wraps the ignore package. Single function: buildIgnoreFilter().

🚶

walker.ts

Recursive async DFS directory walker. Skips symlinks, applies filter, returns flat FileEntry[]. Filters by include glob patterns using micromatch.

📄

summarizer.ts

Reads file contents. Detects binary files via extension set and null-byte scan. Truncates by line count. Handles read errors gracefully.

🔢

tokenEstimator.ts

Two functions: estimateTokens() and formatTokenCount(). Pure functions with no side effects. The entire module is 15 lines.

✏️

formatter.ts

Builds the output header, formats each file block (plain or markdown), and assembles the final string. Contains the 60+ entry language map for syntax highlighting.

🌲

tree.ts

Generates an ASCII directory tree with proper ├── and └── connectors. Uses the same ignore filter as the walker to hide filtered paths.

Data Flow Architecture

Data passes through the pipeline as these TypeScript types:

CLI args + .repo2prompt.json │ ▼ FilterConfig → Ignore (ignore filter object) │ ▼ WalkOptions → FileEntry[] { absolutePath: string relativePath: string }[] │ ▼ (read each file) FileBlock[] { relativePath: string content: string ← may be mutated by budget loop isBinary: boolean wasTruncated: boolean totalLines: number } │ ▼ (format each block) string[] (formatted file blocks) │ ▼ (assemble) string (final output — header + tree + blocks) │ ▼ stdout / file / clipboard

Notice that FileBlock objects are mutated in-place during the token budget loop — the content field is overwritten. This is the one place in the codebase where mutation is used instead of creating new objects. It keeps the budget loop simple but is worth knowing when debugging.

Design Patterns Architecture

Pipeline Pattern

The entire CLI is a linear pipeline where each stage has a defined input and output type. This makes each stage independently testable and the overall flow easy to trace. This is also sometimes called the Chain of Responsibility pattern.

Strategy Pattern (Output Format)

The OutputFormat type ('plain' | 'markdown') acts as a strategy selector. formatFileBlock(block, format) branches on it to produce different output structures. Adding a new format (e.g., JSON) only requires extending one function. 

// formatter.ts — strategy selection
export function formatFileBlock(block: FileBlock, format: OutputFormat): string {
  if (format === 'markdown') {
    return `## ${block.relativePath}\n\n\`\`\`${lang}\n${block.content}\n\`\`\`\n\n`;
  }
  return `=== ${block.relativePath} ===\n${block.content}\n\n`;
}

Layered Configuration (Precedence Chain)

Three layers of configuration are merged with explicit precedence: defaults → config file → CLI flags. Each layer can override the previous. This is the same pattern used by tools like ESLint, Prettier, and webpack. 

// index.ts — CLI flags win over file config
const maxFileLines = opts.maxFileLines ?? fileConfig.maxFileLines ?? 500;

Graceful Degradation

Every I/O operation that might fail is wrapped with a try/catch that returns a safe fallback rather than crashing. Read permission errors, malformed JSON config, missing gitignore — all are silently skipped or logged to stderr without halting execution.

Concurrency Control System Design

Reading files is the most I/O-intensive part of the pipeline. The naive approach — Promise.all(files.map(readFile)) — would open every file simultaneously. On a large repo, this exhausts the operating system's file descriptor limit.

The Batch Semaphore Pattern

The solution is a manual batch loop with a fixed concurrency cap of 50. This is equivalent to a semaphore (or a worker pool) with 50 slots: 

// index.ts — batched concurrent reads
const CONCURRENCY = 50;
const fileBlocks: FileBlock[] = [];

for (let i = 0; i < files.length; i += CONCURRENCY) {
  const batch = files.slice(i, i + CONCURRENCY);
  const results = await Promise.all(batch.map(async (file) => {
    const fc = await readFileContent(file.absolutePath, maxFileLines);
    return { relativePath: file.relativePath, ...fc };
  }));
  fileBlocks.push(...results);
}

Why Exactly 50?

Most Unix systems have a default per-process limit of 1024 open file descriptors. With system files, stdio (0,1,2), and other overhead, 50 concurrent file reads is safely under any reasonable limit while still achieving significant parallelism.

Interview angle: "I chose a batched concurrency model with Promise.all to parallelize I/O without exhausting file descriptors. The 50-file cap is a pragmatic safety margin well under the OS limit."

Configuration Layering System Design

The tool accepts configuration from two sources, merged with a clear precedence order. This design lets users set project-level defaults while always being able to override them from the command line.

maxFileLines.repo2prompt.json → maxFileLines--max-file-lines
maxTokens.repo2prompt.json → maxTokens--max-tokens

Note that exclude and include patterns are additive: config file patterns and CLI patterns are merged into a single array. This lets you define base exclusions in the config and add temporary ones at the CLI.

Unix Philosophy System Design

The CLI follows core Unix design principles:

stdout for data, stderr for diagnostics

All file content goes to stdout so it can be piped. The summary line (✓ 42 files | ~18,400 tokens) always goes to stderr so it's visible even when piping output.

Do one thing well

Reads a directory, produces text. No transformation, no analysis, no inference. This makes it composable with other tools via pipes.

Silent success

The tool writes nothing to stdout when --output or --copy is used — only the stderr summary. Programs should not print unnecessary output on success.

Non-zero exit on error

All caught errors call process.exit(1) with a message to stderr. Piped workflows can detect failure through exit codes.

DFS Tree Traversal DSA

The core algorithm for discovering files is a recursive Depth-First Search (DFS) over the file system tree. The walker visits a directory, then recurses into each subdirectory before moving to the next sibling — the classic pre-order DFS.

Why DFS (not BFS)?

  • DFS uses a call stack (O(depth) space) instead of a queue (O(width) space). File trees are typically deep, not wide.
  • DFS naturally produces paths grouped by directory, which makes the output more readable.
  • The ignore filter can prune entire subtrees early: when a directory is ignored, the recursion simply doesn't happen.

The Actual Implementation

// walker.ts — recursive async DFS
async function walkDir(
  dir: string,
  rootDir: string,
  ignoreFilter: Ignore,
  results: FileEntry[],  // output accumulator — passed by reference
): Promise<void> {
  const entries = await readdir(dir);

  for (const entry of entries) {
    const absolutePath = join(dir, entry);
    const relativePath = relative(rootDir, absolutePath).replace(/\\/g, '/');

    // Skip symlinks to prevent infinite loops
    if (entryStats.isSymbolicLink()) continue;

    // Prune entire subtrees — this is what makes DFS efficient here
    if (ignoreFilter.ignores(relativePath)) continue;

    if (isDir) {
      await walkDir(absolutePath, rootDir, ignoreFilter, results); // recurse
    } else {
      results.push({ absolutePath, relativePath }); // leaf node → add to output
    }
  }
}

Complexity

  • Time: O(N) where N = number of files and directories visited. Each node is visited exactly once.
  • Space: O(D) call stack depth where D = max directory depth. Plus O(F) for the results array where F = number of matching files.
  • Pruning: When a directory is ignored, none of its children are visited — the effective N is much smaller than the total file count.

Greedy Token Budget DSA

When the total output exceeds --max-tokens, the tool must reduce the output size. It uses a greedy algorithm: sort files by size descending, then remove or truncate the largest ones first until the budget is met.

Why Greedy?

The optimal solution (minimize files removed while staying under budget) is essentially the Knapsack Problem, which is NP-complete. For a CLI tool that needs to run in milliseconds, greedy is the right trade-off: it finds a good (though not always perfect) solution in O(N log N) time.

The Algorithm

// index.ts — greedy token budget reduction

// Step 1: Sort non-binary blocks largest first — O(N log N)
const nonBinaryBlocks = fileBlocks
  .filter(b => !b.isBinary && b.content.length > 0)
  .sort((a, b) => b.content.length - a.content.length);

let remaining = totalTokens - maxTokens; // tokens we need to remove

// Step 2: Greedily remove until budget is met — O(N)
for (const block of nonBinaryBlocks) {
  if (remaining <= 0) break;
  const blockTokens = estimateTokens(block.content);

  if (blockTokens <= remaining) {
    // This file is smaller than what we still need to remove — drop entirely
    remaining -= blockTokens;
    block.content = '[file omitted: token budget exceeded]';
  } else {
    // This file is larger than needed — partially truncate it
    const keepChars = (blockTokens - remaining) * 4;
    // ... truncate block.content to keepChars characters by lines
    break;
  }
}
Nuance: The algorithm processes the largest file first. If that file alone covers the entire excess, it's partially truncated and the loop exits. If it's smaller than the excess, it's dropped entirely and the loop continues. This means smaller files are always dropped before larger ones are partially truncated — a "drop whole files first" strategy.

Complexity

  • Sort: O(N log N) — standard comparison sort
  • Greedy loop: O(N) — one pass through the sorted list
  • Overall: O(N log N) dominated by the sort

Binary File Detection DSA

Including binary files (images, executables, fonts) in the text output would produce garbage. The tool uses a two-layer detection strategy:

Layer 1: Extension Set Lookup — O(1)

A Set of ~40 known binary extensions (.png, .exe, .zip, etc.) is checked first. Set lookup is O(1), making this the fast path for known binary types. 

const BINARY_EXTENSIONS = new Set([
  '.png', '.jpg', '.gif', '.webp',  // images
  '.mp3', '.mp4', '.wav',           // media
  '.zip', '.tar', '.gz',            // archives
  '.exe', '.dll', '.dylib',         // binaries
  // ... ~40 total
]);

function isBinaryExtension(filePath: string): boolean {
  return BINARY_EXTENSIONS.has(extname(filePath).toLowerCase());
}

Layer 2: Null-Byte Content Scan — O(min(N, 512))

If the extension isn't recognized, the file's first 512 bytes are scanned for null bytes (0x00). Binary files almost always contain null bytes; text files almost never do. Scanning only 512 bytes keeps this fast regardless of file size. 

function hasBinaryContent(buffer: Buffer): boolean {
  const checkLength = Math.min(buffer.length, 512);
  for (let i = 0; i < checkLength; i++) {
    if (buffer[i] === 0) return true;
  }
  return false;
}
This is the same heuristic used by Git to detect binary files when deciding whether to show a diff. It's a well-established technique in the industry.

Glob Pattern Matching DSA

Two separate pattern-matching systems handle file filtering:

1. Ignore Filter — gitignore semantics (the ignore package)

Used for --exclude patterns and .gitignore. The ignore package implements the full gitignore specification, including negation patterns (!important.ts), directory-only patterns (docs/), and relative patterns.

2. Include Filter — glob semantics (micromatch)

Used for --include patterns. After the walker collects all non-ignored files, micromatch filters the result list by the include patterns. Supports ** (any depth), * (any name), and brace expansion like *.{ts,js}. 

// walker.ts — include filtering applied after full walk
return results.filter((f) =>
  micromatch([f.relativePath], options.includePatterns, { dot: true }).length > 0
);

Why Two Libraries?

Gitignore patterns and glob patterns have different semantics. ignore is optimized for gitignore-style exclusion (stateful, layered). micromatch is optimized for shell-style glob matching (stateless, per-file). Using the right tool for each job avoids edge-case bugs from trying to unify them.

Path Normalization

On Windows, path.relative() returns backslash-separated paths. Both ignore and micromatch expect forward slashes. Every relative path is normalized with .replace(/\\/g, '/') before any pattern matching.

What to Say on Your Resume

"Built a TypeScript CLI tool that recursively walks codebases, applies layered ignore filtering, and produces optimized text output — featuring async batched I/O, a greedy file-trimming algorithm, and dual output formats (plain text and Markdown with syntax highlighting)."

Architecture Questions

"Walk me through the architecture."

8-stage linear pipeline. Each stage owns one responsibility. Data flows as typed interfaces between stages: Config → Ignore filter → FileEntry[] → FileBlock[] → string.

"How do you handle configuration?"

Three-layer precedence: hardcoded defaults → .repo2prompt.json → CLI flags. Same pattern as ESLint/Prettier. CLI flags always win. Exclude patterns are additive across layers.

"How would you add a new output format?"

Add a new value to the OutputFormat union type in formatter.ts, then add a branch in formatFileBlock(). No other files need changes.

System Design Questions

"How do you handle large repositories?"

Batched concurrent reads (50 at a time) to avoid file descriptor exhaustion. Token budget with greedy trimming. Line-level truncation for individual large files.

"What happens on read errors?"

Graceful degradation everywhere. Failed reads return an error message string instead of throwing. Permission-denied directories are silently skipped. The tool never crashes on I/O errors.

"How does stdout vs stderr work?"

File content always goes to stdout (pipeable). The human-readable summary (file count, token count) always goes to stderr (always visible). This follows Unix convention.

Algorithm/DSA Questions

"What algorithm does the file walker use?"

Recursive async DFS. Ignore filter prunes entire subtrees early — when a directory is filtered, we never recurse into it. O(N) time over visited nodes.

"How does the token budget work?"

Greedy algorithm: sort files by size descending, remove largest first. O(N log N). An approximation of the NP-hard knapsack problem — optimal algorithm would be too slow for a CLI.

"How do you detect binary files?"

Two-layer: O(1) extension Set lookup first, then O(512) null-byte scan of file header. Same heuristic Git uses. Early exit avoids reading the full file for known binary extensions.

Architecture

What TypeScript type carries file data from the walker to the formatter?
FileBlock[] — each block has relativePath, content, isBinary, wasTruncated, and totalLines.
Which module is responsible for detecting and skipping binary files?
summarizer.ts — via extension set lookup and null-byte scanning. The walker doesn't know about binary status.
In what order are config layers applied, and which wins?
Defaults → .repo2prompt.json → CLI flags. CLI flags always win (highest precedence). Exclude patterns are merged (additive).
Why does the tree generator have its own directory traversal instead of reusing the walker?
Architectural gap — they were built separately. Both implement similar DFS logic independently. This is duplicate code and could be unified, but it works correctly as-is.

Algorithms

What is the time complexity of the file discovery (walker)?
O(N) where N is the number of nodes visited. With ignore pruning, N is often much smaller than the total file count. Each node is visited exactly once.
Why use greedy for token budget trimming instead of an optimal algorithm?
The optimal solution is NP-hard (Knapsack Problem). Greedy runs in O(N log N) — fast enough for a CLI. The greedy solution is a good approximation and the exactness doesn't matter here.
How many bytes does the null-byte binary scan inspect, and why that number?
512 bytes. This is enough to reliably detect binary content while keeping the check cheap. Binary files almost always have null bytes in the first 512 bytes; text files almost never do. This is the same heuristic Git uses.
Why is path normalization to forward slashes necessary in the walker?
On Windows, path.relative() returns backslash-separated paths. Both the ignore and micromatch libraries expect forward slashes. Without normalization, pattern matching would silently fail on Windows.

System Design

Why is file reading limited to 50 concurrent operations?
The OS limits open file descriptors per process (typically 1024 on Unix). Reading all files simultaneously could exhaust this limit. 50 concurrent reads is a safe cap that still provides meaningful parallelism.
Why does the summary line always go to stderr, not stdout?
Unix convention: stdout is for data (pipeable), stderr is for diagnostics. If the summary went to stdout, it would contaminate the output when piping to another program.
What does the --diff flag do, and what could go wrong with it?
It runs git diff --name-only <ref> and uses the changed files as the include list. The ref comes from user input and is passed unquoted into a shell command — a potential shell injection vulnerability if the ref contains shell metacharacters.
